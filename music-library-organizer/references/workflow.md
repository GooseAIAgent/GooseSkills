# 音乐库整理工作流（实战验证）

源自对多个真实音乐库（共数千首 FLAC/MP3，含海来阿木、IU、毛不易、薛之谦、周杰伦、田馥甄等，按专辑/年份组织）的整理实践。执行任何任务前先通读对应的流程，并严格遵守「安全红线」。

## 通用安全红线（每个任务都要遵守）

1. **试运行先行**：任何批量改名/移动，先生成完整计划清单逐条检查，再实际执行。
2. **NFC 归一化**：macOS 文件名有 NFC/NFD 差异，比较/匹配前一律 `unicodedata.normalize('NFC', s)`。韩文、中文文件名尤其常见匹配失败。
3. **移动用 `/bin/mv` 子进程，不用 `shutil.move`/`os.rename`**：部分卷宗（疑似 NAS）会出现「目标已写入但源未删除」的幻影副本。移动后必须 MD5 校验源与目标：内容相同 → 源是幻影副本，移入「重复文件待核对」文件夹；不同 → 立即停下人工核查。
4. **删除极谨慎**：删除前逐项验证（如 MD5 证明是重复副本）。卷宗可能无废纸篓，删除不可恢复——必须先征得用户确认。空文件夹用绝对路径 `/bin/rmdir` 直调可绕过误拦截。
5. **伴生文件同步**：改名歌曲时同步改名同名 `.lrc` 歌词，以及 `.cover/` 隐藏文件夹里 `<原名>.<扩展名>.<图扩展名>` 命名的封面图。
6. **映射驱动，防遗漏**：分类/改名用「文件名→目标」的显式映射表驱动；发现未登记文件立即报错停下，而不是跳过。
7. **数据可溯源**：专辑名、年份、归属必须来自平台 API 或 WebSearch 核实，禁止编造。查不到的如实告知用户并给出处理选项。

## 任务一：文件名批量修正（删多余后缀等）

场景：删歌名后的数字串（`歌名-歌手-40430817.flac`）、删孤立连字符、批量替换某段文字等。

1. `ls` 摸清命名格式与数量。
2. 写显式转换规则（长词优先防误伤，如「5258-」是歌名一部分不能删）。
3. **冲突预判**：两文件去后缀后重名 → 先报告用户，默认跳过冲突文件。
4. 试运行打印全部「旧→新」，检查后执行，最后校验总数一致。

## 任务二：统一命名「歌手 - 歌名」

用 `scripts/rename_songs.py`：

```bash
python3 rename_songs.py /path/to/music --dry-run   # 先试运行
python3 rename_songs.py /path/to/music --tags      # 文件名歧义时加 --tags 以内嵌标签为准
```

- 规则：「歌手 - 歌名」（空格-连字符-空格）；多歌手「歌手A、歌手B - 歌名」（分隔符 & , ; _ 全部转「、」）。
- 保留歌名后缀：`(Live)`、`(Inst.)`、`(feat. X)`、`（说明）` 等原样不动。
- 倒序文件夹（如「歌名-歌手」）在脚本 `FLIP_DIRS` 登记；个别歧义文件在 `EXPLICIT_MAP` 登记后重跑。
- 顺序判定拿不准时，**以内嵌标签为权威**（读 mutagen 的 artist/title），或用 `music_api.py search` 查证。
- 冲突自动加 " (2)" 后缀（如同一歌手两个同名曲）。

## 任务三：修复内嵌标签（播放器显示异常）

症状：播放器显示 `ifulicn.com-ifulicn.com` 等 → 下载站水印写进了 ID3 标签（title/artist/album/COMM/TCOM/TCON/TPE2 七字段全污），播放器读标签不读文件名。

用 `scripts/fix_tags.py`：

```bash
python3 fix_tags.py /path/to/歌手 --check        # 先检查
python3 fix_tags.py /path/to/歌手                # 从文件名反写，清水印，保封面
```

文件名两种格式都支持（`歌手 - 歌名`、`歌手-歌名`）；专辑名取自「年份-专辑名」文件夹。修完全量复扫校验。

## 任务四：按「年份-专辑名」分类

前提数据：每首歌所属专辑 + 发行年份 + 该专辑总曲目数（判定正规专辑用）。流程：

1. **读内嵌标签**（mutagen）看有无 album/date，有则可信度最高。
2. **逐首查平台**：`python3 scripts/music_api.py search "歌手 歌名"`（QQ 音乐，timePublic 给日期）。数量大时写循环脚本，间隔 1.2–2.5s 防限流，结果存 JSON。
3. **拉专辑曲目数**：`python3 scripts/music_api.py {albummid}` → 判定用。
4. **归类判定**（按用户给定规则执行，以下是本库用过的两种）：
   - 规则A（曲目数）：官方曲目 >5 首的正规录音室专辑 → `年份-专辑名`；单曲/EP/OST/综艺Live/群星合辑 → `年份-合辑`。
   - 规则B（严格专辑）：一律按官方专辑归属 → `年份-专辑名`，哪怕每文件夹只有一两首。
5. **边界判定原则**（遇到时向用户说明）：
   - 「原创首发优先」：歌曲后收入某专辑但首发是 OST/单曲 → 按首发归；用户可要求改为「以专辑收录为准」。
   - 精编版/纪念版 → 归入精编版专辑自身（年份以其发行年为准），不归原专辑。
   - 同歌多版本（独唱/合唱/DJ版）可能属不同专辑，逐版本判定。
   - 群星翻唱合辑（多名歌手各翻几首）不算该歌手的正规专辑。
6. **生成映射表 JSON → `organize_music.py --dry-run` → 检查 → 执行**。
7. 校验：移动前后文件总数一致、无文件丢失。

### 按纯年份合并（不分专辑）

把既有「年份-专辑名」文件夹中的文件全部上移合并到 `年份` 文件夹：遍历、`/bin/mv`、MD5 防幻影、空文件夹用 `/bin/rmdir` 清理（非空遗留要报告）。

## 任务五：外语歌名统一为「本国原名（中文译名）」（脚本 9）

**默认约定，不需要用户每次交代**：韩语、日语等外语歌曲，文件名统一为

```
歌手 - 本国原名（中文译名） [原版本后缀]
```

原名与译名都来自平台数据或人工核实表，**不做翻译创作**；查不到原名的一律保持原样并点名。

### 流程

1. `--scan-only` 先看本地候选量（标题含中文、且不含本国文字的文件）。这一步不联网，秒出。
2. 预览（默认 dry-run，联网）：逐首查 QQ 音乐，按「语义 + 歌手 + 时长」三重校验挑原名，输出完整清单与 `rename-record.csv`。
3. 人工扫一遍清单：`high` 直接过；`medium` 抽查（尤其时长差 3–6s 的现场版、翻唱版）。
4. 确认后 `--apply`：改文件名 → 同步同名 `.lrc` → 写 `title` 标签 → 回写记录表状态。

```bash
S=<本技能目录>/scripts
python3 $S/native_title_rename.py /path/to/music --scan-only
python3 $S/native_title_rename.py /path/to/music --artist IU
python3 $S/native_title_rename.py /path/to/music --artist IU --apply
python3 $S/native_title_rename.py /path/to/music --overrides ov.json --min-conf high --apply
```

### 七个必须绕开的坑

1. **QQ 的 `title` 才是「原名 (中文译名)」，`name` 只有原名**。别拿网易云的 `name` 当原名：它常已被官方译成中文（`坏日子` 的原名是 `싫은 날`，网易只给中文）。
2. **按时长排序会配错歌**。实测「蜡笔」按时长最近会被配成完全不相关的曲目；必须先按语义（本地中文名是否出现在候选 `title` / 字面重合度）、再按时长。
3. **搜索结果的顺序/候选集每次都不一样**（同一 query 两次可能给出不同候选），所以 `medium` 条目要抽查；关键曲目写进 overrides 固定下来。
4. **后缀里可能藏着重复译名**：`凝视(望过之后)` 的括号本身就是译名，改名后要丢掉，否则变成 `…（凝视） (望过之后)`。
5. **曲名里带合作歌手**（`잔소리(WITH 2AM 슬옹)`）要原样保留在原名里，不要清洗括号——那是官方原名的一部分。
6. **中文翻唱/别人的中文歌**（`喜欢你`、`斑马斑马`、`囍帖街`）没有韩文原名，脚本会因「歌手不符」或「无符合语言条件的候选」跳过——这是正确行为，别硬加译名。
7. **macOS 把韩文存成 NFD**：改名后肉眼正常，但 `[\uAC00-\uD7A3]` 检测为 0。校验脚本要先 `unicodedata.normalize("NFC")`，否则会误判「没改成」。

### 人工核实表 ov.json

```json
{
  "IU|毕业日":        {"native": "졸업하는 날",   "zh": "毕业日"},
  "IU|煎蛋的梦想(Live)": {"native": "계란후라이",  "zh": "煎蛋的梦想"},
  "米津玄師|打上花火":   {"native": "打上花火",    "zh": "烟花"}
}
```

键是 `文件名里的歌手|文件名里的中文标题`（后缀一并写进标题）。平台查不到、或用户明确指定译名时用它。

## 任务六：纯年份目录补全专辑标签（标签全空 / 只有年份文件夹）

场景：某歌手目录按 `2016/ 2018/ 2019/ …` 纯年份分，歌曲内嵌标签**整片为空**，
播放器里专辑列全是「未知」；或专辑名缺失、只有年份。此时 `fix_tags.py` 无解
（它从「年份-专辑名」文件夹取专辑，纯年份目录取不到），需要走平台核实。

用 `scripts/album_tags.py`：

```bash
python3 album_tags.py /path/to/歌手 --dry-run     # 用已有缓存出计划，不联网
python3 album_tags.py /path/to/歌手               # 查询 + 写入
python3 album_tags.py /path/to/歌手 --write-only  # 只写缓存，不重新查询
python3 album_tags.py /path/to/歌手 --cache x.json --sleep 2.5
```

写入字段：`title` / `artist`（从文件名反写）、`album` / `date`（平台核实）、
`albumartist`（默认取目录名）。封面不动（FLAC 的 picture 块与 vorbis comment 分离，不会误删）。

流程：

1. **先看现状**：统计有多少首标签为空、有多少首已有 album。已有完整标签的不必重查。
2. **试运行看出计划**：`--dry-run` 只读缓存，先把「能写多少、缺多少」摆出来。
3. **联网查询**：脚本逐首走 QQ 音乐 `search`，结果落 JSON 缓存，可断点续跑。
4. **人工抽查异常匹配**：重点看「专辑名 == 歌手名」「XX的电台」「XX精选集」这类
   合辑型专辑名，多半是配错了正主单曲。
5. **写入并全量复检**：写完扫一遍，确认无空值、无水印、`title`/`artist` 与文件名一致。

### 三个必须绕开的坑

**坑 1：空结果不是「查不到」，是限流。**
QQ 音乐 `search` 被限流时**返回空列表而不报错**。特征极其明显：未命中集中在
**连续编号区间**（实测 90 首里第 26–37、54–68 整段全空）。
对策：空结果退避重试（间隔 4/8/12s），别直接记为未找到。
实测首轮 90 首「未找到」33 首，重试后只剩 1 首，其余全是限流假象。

**坑 2：候选排序错了会把单曲配到合辑。**
若只按「日期最早」排序，`浪子心` 会被配到更早的合辑《海来阿木的电台》，
而不是它自己的单曲专辑《浪子心》(2020-11-18)。
正确优先级：**专辑名 == 歌名**（单曲特征）→ **年份与所在文件夹一致** → 日期最早（原创首发）。

**坑 3：带版本标记的曲目不要按去括号后的歌名找专辑。**
`青山一别(民谣版)` 去掉括号后是 `青山一别`，会命中原版专辑《青山一别》(2020-04-28)。
应保留括号做**专辑名归一后比对**，才能选中《青山一别 (民谣版)》(2020-06-29)。
反过来也要防：目标**不带**版本标记时，必须排除专辑名里带 `DJ/Remix/Live/伴奏/纯音乐/翻唱` 的候选——
否则《没咯》会被配到《没咯 DJ Echo寒羽版》。脚本已内置这条过滤。

**坑 4：平台日期字段会返回 `0000-00-00` 或带时间/点号。**
`0000-00-00`、`2019-10-15 11:06:00`、`2023.04.07` 都要归一成 `YYYY-MM-DD`，
无效日期留空，**不要原样写进标签**。另外平铺目录（如 `难忘歌曲/`）的文件夹名不是年份，
绝不能拿来兜底当 date。

### 与重复文件判定的关系

批量整理时若遇到同名文件（如 `X (2).flac`），**用 `FLAC.info.md5_signature` 比对原始 PCM**，
不要看文件大小——FLAC 无损，体积只反映压缩率。
- MD5 相同 → 真重复，移入「重复文件待核对」（不删除）。
- MD5 不同 → 是**不同版本**（独唱/合唱/重制），两首都保留，按平台版本名区分。
同一首歌常有「合唱版 + 独唱版」两个发行，时长可能只差零点几秒。

## 任务七：批量补全歌词 + 封面并封装进标签

场景：库整理完了但播放器/音乐服务器里大量歌曲没有歌词、封面是灰块；或歌词只在别处有，
本地文件干干净净。目标是一次性把两样都写进文件本身，从此换播放器、换 NAS 都不丢。

### 为什么要写进标签，而不是只放 .lrc

- 只放 `.lrc`：支持伴生文件的播放器能显示，但手机、车载、部分音乐服务器不认。
- 只写内嵌：部分音乐服务器（尤其飞牛音乐这类以文件系统为索引的）只扫伴生 `.lrc`，
  内嵌标签里的歌词不一定会被读出来。
- **两处都写**才通用。脚本默认就是这么做的（`--no-sidecar` 可关掉 `.lrc`）。

### 流程

1. **扫状态**：`python3 scripts/scan_tag_state.py /path/to/music`
   产出「共 N 首 / 有歌词 x / 有封面 y」，并把每首的标题、艺术家、时长缓存进状态文件。
   时长很关键——匹配要靠它排除同名不同版本（原版 4:12 vs Live 5:30）。
2. **试跑看量**：`python3 scripts/lyrics_cover_embed.py --lib /path/to/music --dry-run`
   列出待处理首数与样例清单，先确认没有把整个库误判成「全缺」。
3. **先小批验证**：`--limit 20`，然后抽 2–3 首实际打开播放器/`mutagen` 检查，确认歌词能滚、
   封面不是糊图，再放开全量。
4. **正式跑（放后台）**：数千首级别约 0.5–2 小时。`--workers 3~6` 之间，
   越高越容易触发网易云 IP 级限流。
5. **补第二遍**：第一遍必然有一批「无源」。换了网络环境、或补齐 `--alias` 别名表后再跑一遍，
   仍会有一小撮彻底没有公开歌词（纯音乐、冷门方言歌、未发行 demo），**这是数据本身没有，
   不是脚本失败**，如实报告即可。
6. **通知用户重扫媒体库**：若歌词是给 NAS 音乐服务用的，补完后需在服务端「重新扫描/刷新元数据」，
   否则前端仍显示旧的空状态（见下方坑 5）。

### 数据源优先级与失败回退

歌词：
1. 网易云 `/api/song/lyric`（`lv=1,tv=-1` 同时取翻译），命中率高、带精确时间轴；
   有翻译时按同时间戳插到原文下一行，一句外文一句中文，播放器上体验最好。
2. lrclib.net：免费开放歌词库、不限流，网易云 405 或被墙时的主力兜底；
   用 `syncedLyrics` 字段（纯文本 `plainLyrics` 不带时间轴，不要用）。

封面：
1. 同目录 `.cover/<音频名>.jpeg|png`（既有的整理产物，避免重复下载）；
2. 网易云专辑图 `picUrl?param=NyN`；
3. QQ 音乐 `https://y.qq.com/music/photo_new/T002R500x500M000{album_mid}.jpg`
   —— **独立图片服务器，完全不受网易 API 限流影响**，实测是覆盖最广的一路；
4. iTunes Search API `artworkUrl100` → 替换成 `600x600bb`，全球曲库、几乎不限流。

### 五个必须绕开的坑

**坑 1：网易云 405 是 IP 级限流，不是「没这首歌」。**
批量跑几千首后，`/api/song/detail`、`/api/song/lyric` 会连续返回 `code:405`，
且**空闲一段时间也不会立刻恢复**（实测可长达数小时）。如果把它当成「无封面源」记录，
就会一次性废掉几百首本可命中的歌。
对策：请求间隔 ≥0.6s + 连续 3 次 405 立即熔断 5 分钟，熔断期间把封面任务整体让给 QQ/iTunes；
「无源」的结论只在**真正拿到 200 响应但字段为空**时才记。

**坑 2：`code` 不检查会把限流写成「无封面」。**
`d.get("songs")` 在 405 时是空的，代码会正常走「没取到图」分支并记成确定性无源。
必须显式校验 `code not in (200, None)` 就抛异常，让外层重试与熔断生效。

**坑 3：纯音乐占位歌词会污染整库。**
网易云对无词曲目返回「纯音乐，请欣赏」或「此歌曲为没有填词的纯音乐，请下载…」。
这类文本有十几字、也带不了时间轴，写进 `LYRICS` 后播放器会显示一行静止的说明文字。
脚本用正则过滤（`纯音乐|没有填词的|instrumental|请欣赏` 且长度较短），**发现就当作无歌词**，
继续走 lrclib。

**坑 4：同名不同版本会配错歌词。**
`后来` 有原版、Live 版、DJ 版，时长差几十秒但歌名完全相同。只按歌名匹配必然错位。
必须三重校验：歌名归一后全等 + 歌手有交集 + **时长差 ≤2s**；`--dur-tol` 可调，
但不要为了多命中而放宽到 10s 以上。

**坑 5：NAS 音乐服务只在首次入库扫描时读歌词。**
飞牛音乐、Navidrome、Jellyfin 这类以目录为索引的服务，识别顺序是
「内嵌标签 → 同目录同名 `.lrc`」，但**元数据在入库那一刻就落库了**。
入库之后再往目录里补 `.lrc`，前端不会自动出现歌词，`refetch` 也未必触发。
两种处理：
- 新歌：先补齐 `.lrc`/封面，再让服务端扫描（这是唯一干净的做法）；
- 已入库的存量：补完后到服务端手动「重新扫描媒体库 / 刷新元数据」，或清掉该库缓存重建。
所以批量补歌词这件事，**最佳时机是整理完、入库前**。

**坑 6（补充）：标签名和平台名对不上是命中率的最大杀手。**
库里存的是中文译名（`IU - 唠叨`），平台上只有韩文原名（`잔소리`），搜索自然全空。
建一份 `alias.json` 映射到平台真实名，命中率往往能再提 10–20 个百分点。
同一首歌在 QQ/网易还有 `alias` 字段带中文别名，可用来批量生成这份表。

## 任务八：查重（只读扫描，不删不改）

场景：用户问「库里有没有重复文件」。**先出报告，绝不自动删。**

四层判定（强 → 弱）：

| 层 | 依据 | 含义 | 处置建议 |
|---|---|---|---|
| L1 | 文件 SHA-256 | 字节完全一致 | 保留一份，零损失 |
| L2 | 音频流 MD5（FLAC 用 `info.md5_signature`；MP3 用 `ffmpeg -map 0:a -f md5 -`） | 同一份音频，只是标签/封面不同 | 保留标签更全的一份 |
| L3 | 归一化「歌手+歌名」相同 + 时长差 ≤2s | 同曲多份（单曲版/专辑版/不同母带） | 试听后保留一份 |
| L4 | 同上，时长差 2–8s | 多为 Live/混音/重制 | **不要删**，属不同录音 |

```bash
python3 $S/find_duplicates.py /path/to/music --report dup.csv --json dup.json
```

执行要点与坑：

1. **L1 只在「同文件大小」的桶内算 SHA-256**，否则 100 GB 的库要全量读一遍，纯浪费 IO。
2. **归一化千万不要剥掉版本括号**。`(Live)`、`(Tomorrow Version)`、`(Inst.)` 一旦被剥，录音室版与现场版时长常只差 1–2 秒，会成批误报重复。
3. **现场版专辑要单独识别**：目录名/文件名含 `演唱会|影音|Live|Concert|Tour` 的同名同长曲目，是不同录音，不能当重复。
4. **同曲多版本 ≠ 重复**：单曲版与专辑版母带常不同（响度、混音），删除前应让用户试听确认；报告里必须分级标注，不能只给一个「重复」结论。
5. **报告分级要按「音频是否真的相同」而不是「名字是否相同」**，最终结论只分三类：A 音频完全相同 / B 同曲多份 / C 不同版本（勿删）。
6. 扫描是只读的；**删除永远交给用户确认**，并优先走系统废纸篓（NAS 卷宗可能没有回收站）。
